Link-resolution edge cases

Eight cases a link/URL resolver has to get right, each in its own section below. Some targets deliberately don't resolve to a real page on this site - see the notes in each section for why that's expected.

1. Root-relative link

A link starting with a single slash resolves against the site's origin (scheme + host), not the folder the current page lives in.

Root-relative link to /other-page.html

Note: this repo is hosted as a GitHub Pages project site, served under a repo subpath rather than the domain root. A correctly-resolving crawler will therefore treat this as https://<host>/other-page.html - outside the repo subpath - not .../test-crawl-website/other-page.html. Getting that "wrong" (i.e. resolving it relative to the repo folder instead of the domain root) is the bug this case is meant to catch.

2. Path-relative link

A link with no leading slash resolves relative to the current page's own folder.

Path-relative link to sibling.html

3. Protocol-relative link

A link starting with // keeps the current page's protocol (http/https) but points at a different host.

Protocol-relative link to //example.com/thing

4. Fragment-only link

A link that is only a #fragment stays on the current page and should not be treated as a new URL to fetch.

Fragment-only link back to Section 2

5. mailto: and tel: links

Neither of these is an HTTP(S) resource; a crawler should leave both alone rather than trying to fetch them.

mailto: link

tel: link

6. Normal absolute link (control case)

A fully-qualified URL to an external, unrelated domain. This is the baseline every other case above is compared against.

Absolute link to https://example.com/x

7. Relative link under a <base> tag

A <base href> changes what every relative link on that page resolves against, so this case needs its own document - it can't be demonstrated inline on this page.

Open the base-tag test page

8. Relative link inside a non-standard custom element

Mimics JS-framework markup (e.g. web components, like YouTube's <ytd-*> elements) where the "link" isn't a plain <a> tag, so a naive HTML-to-Markdown converter may not recognize it as an anchor and could pass the href through unresolved, or miss it entirely.
